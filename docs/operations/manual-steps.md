# Manual Environment Steps Register

This is the index of human and out-of-band work. The linked procedures remain the
source of truth for commands; this register is the source of truth for what
silently invalidates each step.

## Routine code deploy versus a new environment

| Routine code deploy preserves | A from-scratch environment build must redo |
|---|---|
| Existing Entra app registrations, app-role assignments, managed-identity principal IDs and Graph grants; Key Vault contents; private endpoints, subnets and DNS links; Logic App connection consent; action-group receivers; Zetta target and credentials; and ADO service connections, variable groups and environment authorisations. | Every applicable row below, in its documented order: tenant-owned identity setup, secret seeding, network inputs, notification consent, delivery details and CI/CD wiring. The Graph row is optional enrichment, and the dev client has no service principal, so no consent can make dev directory-enabled. |
| A full deploy also reapplies the test/prod SWA RBAC overlay and preserves SWA AAD settings only when the committed parameters and overlay path are used. | A new SWA hostname needs the app-registration callback URI updated; a new Function App system identity needs its Graph grant redone. Activate PIM again before any privileged infra operation. |

## Register

| What | Why it cannot be automated | Who | How to verify it is in place | What invalidates it |
|---|---|---|---|---|
| **Activate subscription Owner before infra work.** The deploy identity is currently the Arinco deploy operator's PIM-eligible Owner on the IBP subscription; the identity model records an approximately eight-hour activation window ([as-built identity model](as-built.md#identity-model), [access ownership](access-and-accounts.md#azure)). | PIM elevation is a human privileged-access workflow; an eligible role is not active merely because the identity exists. | Arinco deploy operator; ARN must retain a named PIM-eligible Owner/Contributor path. | An active Owner session can run the subscription-scope `what-if`/deploy and create the resource groups and role assignments. | The activation expires, is removed, or the deploy uses a different identity without the required subscription/RBAC rights. |
| **Create or hand over one Entra API app registration per environment.** Supply its client ID/secret, single-tenant ARN setting, SWA callback URI, ID-token setting and tenant admin consent ([SWA auth prerequisites](../../deployment/README.md#operator-console-authentication-swa--function-app)). | The registration and tenant consent live in ARN's Entra tenant; an Arinco guest cannot create or administer the tenant-owned object. | ARN identity team / app owner; the ARN identity administrator is the recorded Azure identity ask owner. Arinco consumes the resulting IDs and secrets. | A fresh browser round-trip through `/.auth/login/aad` reaches `/.auth/me` and the protected API, as described in the [two-phase SWA verification](../../deployment/README.md#production-swa-auth-bring-up-two-phase--required-for-a-greenfield-prod). | The app registration is deleted/replaced, its secret expires, callback URI or ID-token setting changes, or consent is revoked. Recreating the SWA also changes its hostname and therefore its callback URI. |
| **Assign ARN users/groups to the `Operator` and `Admin` app roles.** Test/prod use the nominated groups (Operators: nominated ARN broadcast-playout operators; Admins: nominated ARN platform owner and operations lead) plus existing direct assignments; the live mappings are recorded in ARN asks §2. **Satisfied in prod — with a transient failure worth knowing about.** Measured 2026-08-12: operators do have working access. `ListJobs` has succeeded 2,574 times against production, most recently 2026-08-13, and there has been **no forbidden request since 2026-08-11T04:06:44Z**. There was a short window of 126 forbidden requests (`caller roles []`) on 2026-08-11 ending at 04:06:44Z — six minutes after `resume.sh` restarted the app at 04:00:38Z following the overnight park. The nominated operators on shift were affected, and the same day logged 2,290 successful operator requests. So the roles resolve correctly once the app is warm; expect a few minutes of empty-role responses immediately after a resume, and do not mistake that for a lost assignment. | App-role membership and group assignment are tenant directory writes controlled by ARN; the deploy pipeline does not own the nominated staff or their group membership. | ARN identity team / ARN identity administrator; nominated ARN group owners maintain membership. | Sign in as a nominated person: `/.auth/me` carries `Admin` or `Operator`, and `/api/jobs` returns 200 rather than 403. | Removing a user/group assignment, changing the app role IDs, replacing the app registration, or revoking tenant consent removes the effective role. |
| **Grant Microsoft Graph application permissions to each Function App system-assigned MI when directory enrichment is wanted.** Use only `Application.Read.All`, `GroupMember.Read.All` and `User.ReadBasic.All`; the exact IDs and paste-run commands are in ARN asks §10, not copied here. | Admin consent is an ARN-tenant operation: the consultant self-grant returned `403 Authorization_RequestDenied`. The grant attaches to the MI service principal, not to code. | An ARN tenant administrator, separately for each Function App MI. | Follow the linked verification block; the Operators page then lists directory role holders with `DirectoryStatus` available. | Deleting/recreating the Function App, or toggling system-assigned identity off then on, mints a new `principalId` and drops every grant. A code/Bicep redeploy preserves it. Dev's client `4671da9f-93b0-49bd-9310-366ede758810` has no ARN-tenant service principal (`Request_ResourceNotFound`), so dev cannot list a directory even with consent. |
| **Grant the deploying user data-plane RBAC before writing locked data.** The private-environment sequence is Owner → Key Vault Secrets Officer and Storage Blob/Queue/Table Data Contributor before seeding and the queue E2E ([private deployment sequence](../../deployment/README.md#deploying-a-private-env-from-outside-the-vnet)). | Test/prod data planes end with public access disabled; an operator outside the VNet cannot write them without an explicit data-plane grant or an in-VNet session. | Arinco deploy operator with active PIM Owner; ARN retains the subscription/RBAC owner path. | The operator can seed Key Vault, enqueue through the documented path, and the Function App reaches `Running` with functions loaded. | Removing the user's data-plane role, changing the operator identity, or deleting/recreating the vault/storage account removes the access. |
| **Seed application, vendor and integration secrets in each environment's Key Vault.** Names include `AiSettings--AzureAI--ApiKey`, `AiSettings--ElevenLabs--ApiKey`, `Here--ApiKey`, `AadClientSecret` and `Webhook--EndpointUrl` ([as-built secrets](as-built.md#secrets-key-vault-ibp-aue-env-kyv-app01); [deployment secret model](../../deployment/README.md#secrets-management)). Playout delivery needs **no secret** — it authenticates with the Function App's managed identity. | Values are vendor- or ARN-owned credentials and must not be put in Bicep, parameter files or source; a human must receive/rotate them and place them in the vault. | Arinco deploy operator seeds vendor values; ARN identity supplies AAD values. | The [existing post-deployment check](../../deployment/README.md#manual-post-deployment-steps) shows Key Vault references on the Function App; `/api/health` reports healthy `keyVault`/`storage`, and one real generation proves HERE, AI and ElevenLabs resolution. | Deleting/recreating the vault, deleting/renaming a secret, expiring/revoking its source credential, or leaving a literal unresolved `@Microsoft.KeyVault(SecretUri=...)` reference undetected invalidates the consumer. In particular, an unseeded `AadClientId` can remain a non-empty literal reference and pass the middleware's empty-value fail-closed check, so verify the resolved value rather than only the app-setting shape. |
| **Use the temporary public-access round-trip when seeding test/prod from outside the VNet.** Enable Key Vault public access, seed, then disable it again; running the same operation from inside the VNet is the alternative ([as-built KV posture](as-built.md#secrets-key-vault-ibp-aue-env-kyv-app01)). | Network-locked Key Vault data-plane writes cannot cross the private endpoint from an external operator; the temporary access is a deployment ordering constraint, not a template secret write. | Arinco deploy operator with the preceding RBAC; ARN network team owns the private endpoint path. | After seeding, Key Vault `publicNetworkAccess` is `Disabled`; the Function App remains `Running` and `/api/health` plus a queue/generation check succeeds over the private path. | A later deploy/override leaves public access enabled, a private endpoint/DNS link is removed, or the vault is replaced without reseeding its secrets. |
| **Bootstrap SWA AAD settings in two phases with `configureSwaAadKeyVaultSettings`.** Deploy phase 1 with `false`, seed AAD secrets, then set `true` and redeploy; leave it `true` thereafter ([production SWA bring-up](../../deployment/README.md#production-swa-auth-bring-up-two-phase--required-for-a-greenfield-prod)). | ARM resolves `getSecret('AadClientSecret')` at parameter-binding time before resources exist, so a greenfield environment cannot complete in one pass without a pre-existing vault and secret. | Arinco deploy operator; ARN identity team supplies the app values. | The phase-2 browser check is `/.auth/login/aad` → `/.auth/me` with `Admin`/`Operator` → `/api/jobs` 200, not only `/api/health`. | Setting the flag back to `false` on a later deploy drops the SWA AAD settings and makes `/.auth/login/aad` return 404; rotating the secret without a phase-2 redeploy leaves the SWA's plain copy stale. |
| **Retain the test/prod SWA custom-provider RBAC overlay.** The pipeline and `deploy.sh` apply `deployment/static-web-app/staticwebapp.rbac.config.json`; dev/sbx intentionally use the built-in provider ([provider paths and prior regression](../../deployment/README.md#operator-console-authentication-swa--function-app)). | The overlay is an artifact/path choice, not a durable Azure resource setting. A direct or alternate manual SWA artifact deploy can silently omit it, as the old Test path did. | Arinco deploy operator and pipeline maintainer; ARN identity team owns the provider's app registration and roles. | On test/prod, a fresh sign-in returns the expected `Admin`/`Operator` in `/.auth/me` and `/api/jobs` is 200; a deploy log shows the RBAC overlay path. | Deploying the shared built-in `web/public/staticwebapp.config.json` to test/prod, bypassing the overlay, or changing the provider file/roles source reverts role mapping to the wrong provider. |
| **Choose the Teams channel and set `teamsGroupId`/`teamsChannelId` for the Logic App.** New-channel and module-deploy steps are in [notification bring-up 1–2](notifications.md#bring-up-in-a-new-environment-fully-programmatic-10-min); prod currently uses an interim Project B10 channel. | The target team/channel is ARN-owned, and guest identities cannot create private channels or teams; the correct ops destination is a human ARN decision. | ARN Teams/ops owner (the ARN operations lead is the recorded channel-nomination contact); Arinco updates the environment parameters. | A wiring payload produces a successful Logic App run and a rendered card in the nominated channel, as in the [current wiring table](notifications.md#current-wiring-read-only-status-checked-2026-07-28-original-bring-up-2026-07-05). | The channel/team is deleted, renamed, access is removed, or either ID changes without updating the parameters and reauthorising the connection. |
| **Complete Teams API connection OAuth consent for each Logic App.** The connection is expected to deploy Unauthorized; use the existing [consent procedure](notifications.md#bring-up-in-a-new-environment-fully-programmatic-10-min) and the [ARN-native account gotcha](notifications.md#consent-gotcha-proven-2026-07-05). | OAuth requires interactive human consent in the ARN tenant. Consenting as the Arinco guest can show Connected while minting a token for the wrong tenant and every post then fails 401. | An ARN-native account authorised to post to the channel; current verified account is an ARN-native operations account, with ARN Teams owner approval. | The connection reports `overallStatus: Connected` and `authenticatedUser` is the ARN-native account; a test payload completes the Logic App run and card action. | OAuth token expiry, password/account changes, wrong-tenant consent, lost channel access, or recreating the connection invalidates consent even if the resource still says Connected. |
| **Provide the private-endpoint subnet and private DNS zones/links for private environments.** ARN hub deployments supply the PE subnet and DNS IDs; a self-served `createNetwork=true` build creates the VNet, delegated integration subnet, PE subnet and zones. Include the five service zones plus the later `privatelink.services.ai.azure.com` and `privatelink.openai.azure.com` additions ([network model](../../deployment/README.md#self-served-private-environment-createnetwork); prod hub ask). | Prod's hub VNet, subnet allocation and DNS forwarding are ARN-managed resources outside this subscription; placeholders intentionally fail validation and the pipeline cannot allocate in that hub. | ARN network team, recorded as owner of PE/DNS inputs; Arinco deploy operator wires the supplied IDs/parameters. | The [as-built inventory command](as-built.md#as-built--deployed-environments) lists the PEs, VNet, zones and links; with public data access disabled, the host is `Running` and functions are loaded. | Subnet deletion/resize, VNet migration, DNS zone unlink/record/forwarder loss, or stale parameter IDs breaks private resolution and data-plane reachability. |
| **Replace interim action-group receivers with ARN on-call email/SMS.** The exact per-environment update is kept in ARN asks §1; move the confirmed values into `main.{dev,test,prod}.bicepparam`. | Receiver addresses and phone numbers are ARN operational decisions; the current Arinco email is only a stop-gap and the central action-group IDs/production lists were not supplied to IaC. | ARN on-call owner; the ARN identity administrator owns the ask, with the operations lead and platform owner coordinating the SMS/DL value. Arinco applies the confirmed parameters. | The action group shows the `ArnOnCall` email/SMS receiver and a test alert reaches that destination; the Teams alert path remains healthy. | Removing/changing the receiver, replacing the action group, or redeploying with stale interim/empty receiver parameters silently sends alerts to the wrong place or nowhere. |
| **Provide the playout drop share and its playout-side identity.** SATISFIED 2026-07-30: ARN built one drop account (`ibpauetststaftp01`), confirmed the `informationbulletins` share IS the production playout folder, and issued the file-name convention (`[SYD]KIIS90s_TRAFF`, `[CAI]STAR1027_TRAFF`, share root, overwrite in place). Both pilot markets delivered from prod the same day. No credential is seeded — the platform writes with its managed identity (`Storage File Data Privileged Contributor`) and Zetta reads with its own on-premises AD identity. | The share, the AD DS join, the autoloader configuration and the playout-side identity are ARN broadcast engineering's and are not creatable by the Azure deployment. | ARN broadcast engineering; Arinco owns the writer, the naming parameters (`zettaFileNamePattern` / `zettaMarketCodesJson`) and the cross-resource-group role assignments. | `zetta.delivery.success` = 1 for the market and the write logged as `<account>/<share>/<name>.wav`; the file then disappearing from the share is Zetta's ingest confirmation. | Renaming the share or account, moving the market's playout code, revoking either drop role, or losing the environment's file private endpoint invalidates delivery while generation still succeeds. A market absent from `zettaMarketCodesJson` fails delivery loudly rather than inventing a file name. |
| **Maintain one ADO ARM service connection per environment.** `IBP-DEV`, `IBP-TST` and `IBP-PRD` use WIF to the IBP subscription and must be authorised for pipeline 108; setup requirements are in [deployment pipeline setup](../../deployment/README.md#pipeline-setup-one-time) and the delivered state in ARN asks §4. | Service connections and their service principals are ADO/ARN-owned security objects; an Arinco guest cannot create or grant their tenant/subscription access. | ARN ADO admin / service-connection owner (the ARN service-connection owner delivered the current set); Arinco pipeline maintainer consumes them. | Pipeline 108 resolves the named connection, authenticates to the IBP subscription and can reach the subscription-scope deployment stage. | Deleting/unauthorising a connection, changing its subscription/RBAC scope, or expiring/revoking its WIF/SP ownership breaks deployments without changing repository code. |
| **Populate and authorise the per-environment ADO variable groups.** `arn-traffic-dev` and `arn-traffic-variables` must carry the documented connection, AAD IDs, Function App name and SWA deployment token; partner secrets remain Key Vault references ([variable-group table](../../deployment/README.md#pipeline-setup-one-time)). | Variable-group permissions, secret links and protected values are ADO admin operations; they cannot be inferred safely from source or committed as plaintext. | ARN ADO admin / pipeline owner; Arinco supplies non-secret parameter expectations. | A supervised pipeline run resolves the group and reaches the intended Function App/SWA; no missing-variable or authorisation error occurs. | Renaming/deleting a group, unlinking its Key Vault secret, changing `functionAppName`/AAD IDs, rotating the SWA token without updating the group, or revoking pipeline authorisation invalidates the stage. |
| **Create/maintain ADO `dev` and `production` environments, approvals and resource authorisations.** The one-time setup requires environment and variable-group authorisation; required approvers are human gates ([ADO setup §3](../../deployment/README.md#pipeline-setup-one-time)). | ADO environment approvals are deliberate human controls and require an ADO admin; the docs explicitly record that an Arinco guest cannot self-grant them. | ARN ADO admin names the environment approvers; Arinco pipeline owner requests/uses the gate. | A supervised run with `enableDeploy=true` reaches the expected `dev`/`production` gate, an approver can approve it, and the stage proceeds to smoke test. | Deleting/renaming an environment, removing an approver, revoking environment/variable-group authorisation, or leaving the stage disabled changes the promotion contract. |
| **Optionally set the `TEAMS_CICD_WEBHOOK` protected pipeline variable.** It is the external Teams/Power Automate URL used by `NotifyOnFailure` ([pipeline setup §4](../../deployment/README.md#pipeline-setup-one-time); [notification architecture](notifications.md#architecture)). | The webhook endpoint is an external Teams/Power Automate secret and must be provisioned and rotated by its owner; an empty value is intentionally a no-op. | ARN/Arinco Teams or CI owner who owns the destination; Arinco pipeline maintainer stores it as a protected variable. | A controlled CI failure produces a `NotifyOnFailure` card in the target channel; an unset variable is observable as the documented no-op. | Rotating/deleting the endpoint, changing its SAS/permissions, or clearing the protected variable makes CI failures silent. |
| **Create the optional audit-access Entra group and set `auditAccessGroupObjectId` when ARN wants Content, People & Culture, or Legal access.** The parameter's empty default intentionally leaves evidence restricted to platform identities ([runbook evidence access](runbook.md#audit-evidence-retrieval-compliance-audio-90-days-logs-2-3-yr)). | The group is an ARN tenant directory object and its membership is a human compliance decision, not an application deploy concern. | ARN identity/compliance owner (the ARN identity administrator is the recorded group-creation contact); the Content, People & Culture, and Legal stakeholders are the named consumers. | A nominated member can access the documented audit job/evidence path, while the configured object ID matches the intended group. | Deleting/replacing the group, changing membership, or clearing/changing `auditAccessGroupObjectId` removes the intended audit access. |
| **Rotate AAD, vendor and notification secrets through their owning systems, then refresh consumers.** AAD rotation requires KV plus SWA re-resolution; a Function App holding a Key Vault reference re-reads it on restart; OAuth re-consent uses the [runbook rotation table](runbook.md#secret-rotation). | New values originate with ARN identity, vendors or Teams; the SWA stores a plain deploy-time copy and the Function App/Logic App cache Key Vault references. | ARN identity team for AAD; Arinco/vendor owners for the rest. | The consumer resolves the new value: console sign-in still completes, a real generation proves the vendor keys, and one Teams card proves the webhook. | Rotating in the owning system without updating Key Vault, or updating Key Vault without refreshing the consumer, leaves the old value in use until the next restart or redeploy. |

## When adding a new manual step

Add it as a row in this table in the same change that introduces it. Populate all
five columns, link an existing procedure instead of copying its commands, and
state the event that silently invalidates the step.
